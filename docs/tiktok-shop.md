# TikTok Shop (с 22.10.2026)

Решение владельца 22.10.2026: подключаем, **только чтение**. Custom app «Dnipro-M», рынок Spain · Local. Магазин
берётся из Get Authorized Shops (на 22.10 — один, регион ES, LOCAL); `shop_cipher` берётся из ответа API на каждом
прогоне и нигде не хранится. Код — сразу под несколько магазинов: позже добавятся страны.

## Что есть

- `nb/tiktok_client.py` — модуль: подпись (HMAC-SHA256), белый список путей, обновление токенов, ошибки без секретов.
  Его импортируют ноутбуки TikTok и тесты (`tests/test_tiktok_client.py`).
- `nb/tiktok_auth_exchange.py` — ноутбук `Kabinet - TikTok Auth Exchange`: одноразовый код → токены в скоуп и
  проверочный Get Authorized Shops. Запускает владелец руками.
- Загрузчик в сырьё (`dnipro_m.tiktok`) — следующим PR.

## Только чтение: белый список

Клиент отказывает до запроса во всём, чего нет в `ALLOWED`. POST — ровно два поиска, у TikTok они есть только как POST
и данных не меняют (решение владельца 22.10.2026): `POST /order/202309/orders/search` и
`POST /product/202502/products/search`. Остальное — GET: `/authorization/202309/shops`, `/order/202507/orders`,
`/order/202407/orders/{id}/price_detail`, `/product/202309/products/{id}`, `/finance/202309/statements`,
`/finance/202501/statements/{id}/statement_transactions`, `/finance/202501/orders/{id}/statement_transactions`.
Новый путь — правкой `ALLOWED` по «мержи», и только на чтение. IP allowlist приложения не используем.

## Секреты — скоуп `tiktok-shop`

Ключи с дефисом, как во всех наших скоупах (решение владельца 22.10.2026).
- `app-key`, `app-secret` — вносит владелец (перезаписаны 22.10.2026 12:17 и 12:23); `app-id` — с 17.09, коду не нужен.
- `refresh-token`, `access-token`, `refresh-expires`, `access-expires` (unix, секунды) — пишет ноутбук обмена и сам
  клиент при обновлении. TikTok выдаёт новый refresh-токен при каждом обновлении — клиент записывает его первым и с
  повторами; не записался — `TokenSaveError` и падение: старый refresh уже может не действовать → повторная авторизация.
- Значения агент не читает и не выводит. Ошибки клиента секретов не содержат: у запросов авторизации app_secret и
  auth_code — в query, а исключения requests печатают URL, поэтому сетевые ошибки поднимаются без URL.

## Принципал и права (решение владельца 22.10.2026)

Джоба загрузчика — только под `kabinet-jobs-sp`; `claude-uc-ro` не расширяем и для TikTok не используем. Пока #364 не
смержен и его SQL не применён — загрузчик без расписания, прогоны владелец запускает руками.

Права `kabinet-jobs-sp` (применяет владелец, `<sp>` — Application ID):


Can Read на папку ноутбуков TikTok.

Снять MANAGE у `claude-uc-ro` на скоупе — когда `kabinet-jobs-sp` заработает (применяет владелец):
```

```
На 22.10.2026 у скоупа: MANAGE у владельца и у `claude-uc-ro` (выдан 17.09 для пробы).

## Загрузчик (PR2, `nb/tiktok_loader.py`, `nb/tiktok_rows.py`, `sql/tiktok_schema_2026-10-22.sql`)

- Таблицы `dnipro_m.tiktok`: `raw_orders`, `raw_order_lines`, `raw_products`, `raw_product_skus`,
  `raw_finance_statements`, `raw_finance_statement_transactions`, отметки продолжения — `sync_state`. Запись — MERGE
  по ключу, по частям.
- Первый запуск — `tiktok_history_days` (90). Дальше заказы и выписки — от отметки `sync_state.done_until` (конец
  последнего куска, записанного ЦЕЛИКОМ) минус перекрытие: `tiktok_order_overlap_days` (3), `tiktok_finance_overlap_days`
  (14); куски по `tiktok_window_days` (7). Не по max(update_time): TikTok отдаёт update_time и вне запрошенного
  диапазона, и после сбоя в середине max перепрыгнул бы дыру. Первый сбойный кусок останавливает поток — следующий
  прогон начинает с него. Перечитать поток заново — `full=1` или удалить его строку в `sync_state`. Товары — снимок
  целиком (снятый с продажи SKU остаётся в таблице с последними ценой и остатком). Настройки — `reorder_params`.
- **Персональные данные покупателя в открытом виде в сырьё не пишутся.** У заказов `raw_json` — белый список полей
  (`ORDER_KEEP`, `LINE_KEEP`), а не ответ целиком: имя, адрес, телефон, email, ник, аватар, налоговый номер, сообщение,
  `user_id`, номер отслеживания, заметка продавца, id группы объединения заказов не попадают, и новое поле TikTok без
  правки кода тоже. Из адреса — только индекс и код региона. Для повторных покупок — `buyer_hash = sha256(соль +
  user_id)` (решение владельца 22.10.2026). Это псевдоним: по GDPR (ст. 4(5)) он остаётся персональными данными.
  Соль — секрет `tiktok-shop/buyer-salt`, задаёт владелец; **соль не менять**: другая соль — другие хеши, и прежние
  покупатели перестают узнаваться. Без соли загрузчик не стартует.
- **Доступ к схеме** (на 22.10.2026): у `account users` ALL PRIVILEGES на каталог `dnipro_m`, и `dnipro_m.tiktok` это
  наследует — чтение и запись у всех пользователей и принципалов аккаунта, узкий грант `kabinet-jobs-sp` этого не
  сужает. Решение за владельцем (описание PR #370).
- Пока #364 не применён — без расписания, прогоны владелец запускает руками под своей учёткой (`dry_run=1` — без
  записи в таблицы и пульса; обновлённые токены клиент записывает и в `dry_run`: иначе повёрнутый refresh-токен
  потерялся бы). Джоба под `kabinet-jobs-sp` и правило здоровья `Kabinet - TikTok Shop Loader` — отдельным PR после #364.

## Аналитика (группа 1, `nb/tiktok_analytics_loader.py`, `nb/tiktok_analytics_rows.py`, `sql/tiktok_analytics_2026-10-22.sql`)

- Отдельный загрузчик `Kabinet - TikTok Shop Analytics Loader`, свой пульс. Только GET, семь путей аналитики в белом
  списке клиента. Таблицы `raw_analytics_shop_daily`, `_product_daily`, `_sku_daily`, `_video_daily`,
  `_video_product_daily`, `raw_analytics_lives`, `_live_products`. Дата — день в часовом поясе магазина, до
  `latest_available_date` из ответа (вчера). Продолжение — потоки `analytics_*` в `sync_state` минус
  `tiktok_analytics_overlap_days` (7): атрибуция видео и эфиров дописывается задним числом.
- Пробы 22.10.2026: глубина — около года (январь 2026 отдаётся, октябрь 2025 — «вне окна истории этой версии API»);
  оценка магазина (SPS) для ES не поддерживается (код 38011502) — не грузим; видео — окно запроса не больше 60 дней;
  эфиры требуют `account_type` (OFFICIAL / AFFILIATE / MARKETING, «ALL» не поддерживается), на 22.10 эфиры только у
  креаторов-аффилиатов.
- **`gmv` аналитики = что заплатил покупатель (`sub_total` заказов), `gmv_with_tiktok_co_funding` = выручка продавца
  (`sub_total + platform_discount`)** — сверено по дням 17–21.10.2026 до цента; неоплаченные отмены в GMV не входят.
- Креаторы: `creator_id` и публичный ник `creator_user_name` (решение владельца 22.10.2026); `nick_name` и `open_id` не
  пишутся. У видео `creator_id` в ответе есть; **у эфиров его нет вовсе** (только `open_id`, и он не совпадает с
  `creator_id` того же креатора в видео) — поэтому у эфиров `creator_id` пустой, и склеивать креатора между видео и
  эфирами — по нику.
- Товары эфира (`/analytics/202512/shop/{live_id}/products_performance`) — **по документации TikTok** (на живом API путь
  ещё не вызывался): только для эфиров официальных и маркетинговых аккаунтов, одним ответом без дат и страниц. На
  22.10.2026 у магазина эфиры только у креаторов-аффилиатов (3 за 60 дней, продаж в них нет), поэтому
  `raw_analytics_live_products` пуста, а проверка этой таблицы на живых записях — после первого своего эфира с продажами.
- Глубина первого запуска — общий `tiktok_history_days` (200 с 22.10.2026, поднят под полную историю заказов): с мая.
- **Окно истории аналитики** (проба 22.10.2026): магазин — не меньше года; товары, SKU, видео и эфиры — 180 дней (181 — код 28001022). Загрузчик не идёт глубже `tiktok_analytics_lookback_days` (180) для этих потоков — край считается от `latest_available_date` магазина (его дата, не UTC), с днём запаса; без неё первый прогон с `tiktok_history_days` = 200 упал на 05.04. Первый заказ магазина — 04.05.2026, в окно входит.

- **Товары эфиров** (`raw_analytics_live_products`) смержены непроверенными на живых записях (решение владельца
  22.10.2026) — проверить на первом своём эфире с продажами.
- **TikTok в утренней сводке — только с флагом `reorder_params.tiktok_report_enabled` = 1** (решение владельца 23.10.2026). Строки нет или не 1 — ни «Бизнеса», ни «Техники» по TikTok. Сводка 23.10 в 08:00 ушла с TikTok: #372 выложен в 01:3x, флага тогда не было.
- **Средние и «дни продаж» TikTok считаются с первого заказа (04.05.2026)** (решение владельца 23.10.2026): 12 дней аналитики магазина с 22.04 по 03.05 — нулевые, до первой продажи; в средние и число дней продаж не входят.
- **«Обзор» при `tiktok_overview_enabled` = 0 показывает TTS-ES администратору** (решение владельца 23.10.2026, как
  вкладка на «Площадках»): по роли `admin`, а не `auth.can()` — в режиме раскатки can() отвечает «да» всем. Под строкой —
  подпись «видно только администратору». Остальным ничего; флаг = 1 открывает всем, кто видит «Обзор».
- **Возвраты на вкладке — отдельной строкой** (решения владельца 23.10.2026): выручка продавца — до возвратов, как у
  остальных каналов «Обзора»; возвраты — отрицательная выручка операций выписок, с минусом, — плиткой «Возвраты, до
  возврата комиссии» и колонкой «Возвраты, €» в неделях, с подписью. На 01.05–21.10.2026: −134,94 € (два заказа).
  Период без заказов, но с возвратом (например 07.07), показывает возврат, а не только «заказов нет»; в неделе без
  заказов доля «С выплатой» пустая.
- **Возвраты — по дате выписки возврата** (Мадрид), а не по дате заказа (уточнение владельца 23.10.2026): заказ 03.06,
  возвращённый 07.07, — в неделе 06.07. Сумма возврата — до возврата комиссии; возврат комиссии — отдельной плиткой и
  колонкой, с плюсом. **Знаки во всех таблицах TikTok: всё, что уменьшает выплату (комиссии, возвраты), — с минусом,
  возврат комиссии — с плюсом.** Комиссии — только начисленные (операции продажи), без возврата комиссии.
- **«К выплате» — только по продажам** (решение владельца 23.10.2026, вариант 2): выплата заказа берётся с операций
  продажи (`revenue_amount ≥ 0`) по неделе заказа, а возврат и возврат комиссии — с операции возврата по неделе возврата,
  один раз. В неделях колонка «С продаж, €», и строка складывается: «К выплате» = «С продаж» + «Возвраты» + «Возврат
  комиссий». Заказ 576904648695323030: неделя 01.06 +58,87, неделя 06.07 −58,87, итог 0. На 01.05–21.10.2026 плитка
  та же — 3 564 € (оба возврата внутри периода); меняются недели: 01.06 0,00 → 58,87, 29.06 0,00 → 54,55, 06.07
  54,55 → −4,32, 10.08 0,00 → −54,55. Возврат без даты выписки не пропадает: берётся по дате заказа в периоде,
  показывается предупреждением, строкой «без даты» в неделях и в таблице возвратов (на 23.10 таких 0 из 115).
- **Подсказки «К выплате»** (по проверке #377, поручение владельца 23.10.2026): у плитки — всплывающая подсказка, как
  считается выплата; подпись про НДС — «С продаж» по выписке продажи, возвраты по выписке возврата. «К выплате» по
  возврату берётся из `settlement_amount` целиком; если хоть у одного возврата периода TikTok удержит или вернёт что-то
  сверх возврата и комиссии (например доставку), появляются плитка «Прочее по возвратам», колонка в неделях и в таблице
  возвратов — по одному условию; так на глаз складываются строки недель и таблицы возвратов, а плитки возвратов
  («Возвраты», «Возврат комиссий», «Прочее по возвратам») дают ту часть «К выплате», что идёт от возвратов, с точностью до округления плиток до целых евро (вторая часть —
  выплата с продаж, отдельной плитки у неё нет), и подсказка «К выплате» верна. На
  23.10.2026 у всех 115 операций выплата = выручка + комиссии, плитки и колонки нет.
- **«Данные на ДД.ММ ЧЧ:ММ»** (поручение владельца 25.10.2026): время последней загрузки реплики (`max(loaded_at)` в
  `raw_tiktok_orders`, Киев) — подписью под шапкой вкладки и в подписи под строкой TTS-ES на «Обзоре». Пока у
  загрузчика нет расписания (до #364), реплика обновляется только ручным запуском, и подпись показывает, насколько
  свежи цифры. Порог «старше суток» в код не зашит.
- **Комиссии по колонкам** (решение владельца 25.10.2026): в реплике операций — `commission_tiktok`
  (`platform_commission_amount`), `commission_affiliate` (`affiliate_commission_amount` + `affiliate_ads_commission_amount`
  + `affiliate_partner_commission_amount`) и `fee_other` — остаток до `fee_tax_amount`, в сумме три колонки всегда равны
  итогу. На 25.10.2026 по всем 119 операциям: TikTok −414,77, аффилиаты −318,15, прочие −197,38 (Smart Promotion
  −151,96 и EPR −45,42), итог −930,30 — это вместе с возвратами комиссий; по одним продажам (что показывает плитка):
  −426,92 / −327,52 / −197,38, итог −951,82. На вкладке плитка «Комиссии и сборы TikTok» с разбивкой в подсказке и три
  колонки вместо «Комиссии, €» в неделях. Если хоть у одной операции продажи периода колонки пустые (нет разбивки в
  ответе или загрузчик ещё не дописал), весь период показывается одной колонкой, как раньше. Состав «прочих» в
  интерфейсе не называется — это остаток, и туда же попадут новые сборы и налоги группы `tax` (на 25.10.2026 нулевые).

**WRITE на скоуп первый прогон не проверит.** Access обновляется, когда до конца меньше 48 ч, и тогда загрузчик пишет
новый refresh-токен в секрет; при access до 29.10.2026 10:01 UTC первая запись — после 27.10 10:01 UTC. Без WRITE
загрузчик упадёт с `TokenSaveError`, а старый refresh может уже не действовать — повторная авторизация владельцем.
Поэтому до создания джоб (и в любом случае до 27.10 10:01 UTC) — `databricks secrets list-acls tiktok-shop` и
увидеть `$SP` WRITE.

Обе джобы обновляют один и тот же refresh-токен. Пересекутся они, если загрузчик заказов идёт дольше 15 минут (обычно
3–7) или упал и его повтор (через 10 мин) приходится на 06:45; тогда обновление токена в обеих — гонка. Если это начнёт
мешать — аналитику запускать после заказов (условием «по завершении» или в 07:00). Худший случай аналитики с повтором
кончается около 08:15 — на сводку не влияет: она смотрит только на загрузчик заказов (худший случай — около 07:40).

Работает, если: пульс обеих меток обновляется около 06:37 и 06:55, в заметке нет «сбоев N»; у прогона Run as —
`kabinet-jobs-sp`; сторож (~13:07) — `raw_tiktok_orders` зелёный, тревог `job_health` по TikTok нет. Признак нехватки
прав — `permission denied for table …` (Lakebase), `PERMISSION_DENIED` (UC) или отказ записи секрета в ошибке прогона.

## Справочники: логистика и категории (шаг 1 из групп 2–5, `nb/tiktok_reference_loader.py`, 26.10.2026)

`Kabinet - TikTok Shop Reference Loader` — только GET, раз в неделю (пн 12:00 Киев), `run_as` — `kabinet-jobs-sp`.
Время — после окна 09:30–11:30 и далеко от прогонов заказов (06:30) и аналитики (06:45) с их повторами (худший
случай ~08:15): три джобы делят один refresh-токен, одновременное обновление могло бы его потерять.
Белый список клиента дополнен шестью GET-путями: склады, варианты доставки склада, перевозчики варианта, дерево
категорий, атрибуты и правила категории. POST-поиска в группе нет. Таблицы (`sql/tiktok_reference_2026-10-26.sql`):
`raw_warehouses`, `raw_delivery_options`, `raw_shipping_providers`, `raw_categories` (локаль es-ES),
`raw_product_categories` (лист категории каждого нашего товара — из карточки товара, путь уже в белом списке),
`raw_category_attributes` и `raw_category_rules` (только листья наших товаров: обязательные поля, производитель,
ответственное лицо, размеры упаковки, сертификаты). Снимок — MERGE по ключу, `loaded_at` — время прогона; исчезнувшая
у TikTok строка остаётся со старым `loaded_at`. У складов адрес и контакт не пишутся: из адреса только регион и страна.
Отгрузки по заказам (посылки, трекинг: `/fulfillment/…`) не грузятся — там адрес покупателя и номер отслеживания;
`fulfillment` в этой группе — варианты доставки и перевозчики. Проба `dry_run=1` 26.10.2026 на живом API: складов 2,
вариантов доставки 1, перевозчиков 17, категорий 2040, товаров (кроме удалённых) 62, листовых категорий 25,
атрибутов 546, правил 25, сбоев 0 — запись в `dry_run` не выполняется (MERGE, типы и NOT NULL не проверены), и проба
шла под владельцем; первая проверка записи и прав принципала — первый `run-now` после SQL части A. Работает, если:
пульс `Kabinet - TikTok Shop Reference Loader` обновляется по понедельникам около 12:05 без «сбоев N», у прогона Run as —
`kabinet-jobs-sp`, в семи таблицах `loaded_at` свежий. Опечатка TikTok в атрибутах — `is_requried` — читается вместе с
`is_required`.
- **По проверке #389 (27.10.2026):** склад в `raw_json` — белым списком полей (`WAREHOUSE_KEEP`: `id`, `name`, `type`,
  `sub_type`, `effect_status`, `is_default`, `entity_id`; из адреса — `region`, `region_code`, `state`) — новое поле

## Возвраты и отмены (шаг 2 групп 2–5, `Kabinet - TikTok Shop Loader`, 27.10.2026)

Решение владельца 27.10.2026: POST-поиск возвратов и отмен, только чтение. Белый список клиента дополнен двумя
POST-путями с пометкой «только поиск» — `/return_refund/202309/returns/search` и `/return_refund/202309/cancellations/search`;
тест CI держит правило «любой POST в белом списке — путь `…/search`», решения по возврату и отмене (`…/approve`,
`…/reject`) не проходят. Отдельной джобы нет: два новых потока идут в загрузчике заказов (06:30) — один refresh-токен,
одна джоба — новой гонки за токен нет, но длительность загрузчика растёт, а гонка с аналитикой (06:45) начинается, если он
идёт дольше 15 минут (выше). Поиск — по `update_time` кусками `tiktok_window_days`, с перекрытием

`#…` возврата потребитель берёт, только если настоящих позиций у него нет). Не пишутся ни в колонки, ни в `raw_json` (белый список

покупателя за обратную доставку, ссылки на картинки. Полей покупателя в ответах нет. Реплики в Lakebase и страницы пока
нет — только сырьё.
