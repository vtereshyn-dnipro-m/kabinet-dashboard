- **Уникальность по паре «пул + маркетплейс» снята 28.09.2026, периоды держит триггер** (`sql/pool_members_periods_OWNER_2026-09-28.sql`, выполняет владелец). До этого на `pool_members` висел `UNIQUE (pool_id, marketplace_id)` БЕЗ даты — одна строка на пару навсегда, и маркетплейс, у которого закрыли участие, вернуться в ТОТ ЖЕ пул не мог никогда: повторная вставка падала «duplicate key value violates unique constraint» (нашлось при девяти проверках триггера на живой таблице — там случай «повторное членство в том же пуле» дал отказ, хотя на временной копии проходил: на копии ограничения не было). По ТЗ 004 §11 у членства есть периоды, значит пара с непересекающимися периодами законна.
- **Порядок в этом файле важен, и он одной транзакцией: сначала триггер, потом снятие UNIQUE.** Уникальность была единственным, что не давало завести два ПЕРЕСЕКАЮЩИХСЯ членства в ОДНОМ пуле — триггер от 28.09 смотрел только на чужие пулы (`p.pool_id <> NEW.pool_id`). Снять её, не расширив триггер, значило бы закрыть одну дыру и открыть другую. Теперь условия «другой пул» в триггере нет вовсе: правило одно — у маркетплейса не может быть двух членств с пересекающимися периодами, ни в разных пулах, ни в одном; текст ошибки для своего пула и для чужого разный, потому что и делать в этих случаях надо разное. Проверено на временной копии, заведённой такой, какой таблица станет после правки: 9 случаев из 9, включая главный — возврат в тот же пул после закрытия проходит, а датой до закрытия нет.
- Проверка на карточке пула подтянута под то же правило: сравниваются периоды по ВСЕМ пулам, а не только чужим, и ровно для тех маркетплейсов, которые будут ВСТАВЛЕНЫ (`picked_ids - cur_ids`) — действующих участников пула мы не трогаем, и сравнение их с самими собой ругалось бы на каждое сохранение. В сообщении для своего пула показываются даты прежнего участия.
- **Выход из пула необратим: `pool_members` держит `UNIQUE (pool_id, marketplace_id)` БЕЗ даты.** Маркетплейс, у которого участие закрыли, вернуться в ТОТ ЖЕ пул не может никогда — историческая строка занимает ключ, и повторная вставка падает «duplicate key value violates unique constraint» (проверено на живой таблице 28.09.2026). Это не триггер и не наша проверка, это ограничение владельца. Практическое следствие для перестройки пулов: роспуск Spain односторонний, вернуть туда LM/MM/CF потом можно будет только заменой ограничения у владельца. Заодно это объясняет, почему при девяти проверках триггера на живой таблице случай «повторное членство в том же пуле» даёт отказ, а на временной копии проходил: на копии этого ограничения не было.

- Реестр прогноза (ТЗ 010/011) — `forecast_documents`, `forecast_register`, `forecast_change_log`, вью `v_forecast_current` (с 17.09.2026). Строки, где штуки округлились до нуля при ненулевых евро, выручку теряют — 0,03–0,06 % от месяца; итоги листа по штукам сходятся точно, по евро расходятся на десятки евро из-за отображаемого округления ячеек. Блок «План месяца» на Обзоре (с 17.09.2026 вечера) — три разреза (страна / страна с маркетплейсами / площадка с маркетплейсами), штуки по переключателю, итог в евро по всем объектам плана — одинаковый в любом разрезе; всегда текущий календарный месяц, период страницы туда не передаётся намеренно. С 18.09.2026 план всех четырёх колонок листа лежит на маркетплейсах (AMZ-ES id 1, AMZ-FR id 3, AMZ-DE 2, AMZ-IT 4): лист — «Amazon Product Planning», это план по Amazon, а пул по ТЗ 004 — сумма участников без собственного плана (решение владельца; пуловые записи 6/7 переведены в superseded, `sql/forecast_es_fr_to_marketplaces.sql`). Блок — **только Amazon** (с 20.09.2026): факт из `sales_traffic_daily`, периметр — рынки Amazon с планом или с продажами за месяц; страны без плана (BE, GB) — отдельными строками с нулевым планом (Ярослав, 18.09.2026). Каналы Mirakl (LM-ES, CF-ES, MM-ES, MM-FR) из блока убраны решением владельца: с ними итог блока (48 720 €) расходился с карточкой «Продажи по заказам» (43 547 €, только Amazon) ровно на их продажи — третье расхождение за три дня. Правило периметра осталось: в блоке только Amazon, тот же набор рынков, что в карточке. А вот равенства сумм с 27.09.2026 больше нет, и это намеренно: факт переведён на **дату отгрузки**, карточка считает по дате заказа. Что теперь обязано сходиться — не число, а объяснение: подпись под таблицей называет основание, говорит, почему сумма не равна карточке, и в каком порядке расхождение. Выполнение и темп узла — только по строкам с планом. Таблица на экране сортируется кликом по заголовку, поэтому страна/площадка — отдельная колонка в каждой строке, а не отступ «↳» (после сортировки по «План» CF-ES оказывался «под Бельгией»). Узел из одного маркетплейса без пула — одна строка, не «итого» и тот же рынок под ним: после перевода на только-Amazon у каждой страны ровно один рынок, и разрез «страна с маркетплейсами» задваивал каждую строку (21.09.2026); «итого» появляется, когда участников два и больше (площадка AMZ, будущие пулы/TikTok).
- Факт в план-факте — по **дате отгрузки** (с 27.09.2026, `plan_fact.py`, оба места: «Обзор» и «Деньги»). План сравнивается с тем, что уехало покупателю, а не с тем, что заказали — так требует ТЗ 010 §13 и так считают алерты сторожа. Источник — `shipment_facts` канал `AMZ` (отчёт отгрузок FBA плюс MFN мадридского склада через SendCloud), цена — из строки заказа `orders_history.item_price`: это сумма строки **с НДС**, то есть та же система координат, что у плана из листа. Средняя цена нигде не подставляется. Что важно держать в голове: **суммы с карточкой «Продажи по заказам» теперь расходятся по делу** — в месяц входят отгрузки заказов конца прошлого месяца и не входят заказы, которые ещё не уехали; на сентябре 2026 это 55 404 € против 56 776 € (−2,4 %), по штукам закрытие 91–104 % (BE 91, ES 100, GB 100, IT 102, DE 104, FR 104). Отгрузка, которой не нашлась строка заказа, считается в штуках, но не в евро — их число отдаётся полем `fact_unpriced_units`, и обе страницы подписывают такой факт как неполный с долей (сентябрь: 4 шт из 976, 0,4 %). Пустой процент лучше правдоподобного: подстановка средней цены сделала бы евро гладкими и неверными, а возврат к дате заказа поменял бы основание молча.
- Таблица, созданная `claude_code_rw`, для приложения невидима, пока rw сам не выдаст SELECT принципалу приложения `583bf6d1-…`: так «План месяца» на Обзоре показывал «плана нет» при загруженном реестре (17.09.2026). С 17.09 стоят default privileges от rw в `kabinet_data` на оба принципала, но объекты, созданные до этого, надо было выдавать явно (`sql/app_principal_grants.sql`). Проверка одна: `has_table_privilege('583bf6d1-…', 'kabinet_data.<таблица>', 'SELECT')`. И на странице «не прочиталось» показывать отдельно от «данных нет» — иначе права маскируются под пустоту.
