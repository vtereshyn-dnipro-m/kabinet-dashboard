- Нормативы покрытия по ТЗ «Остатки» §9 (с 27.09.2026) — свой реестр `kabinet_data.coverage_norm_rules`, а НЕ колонки в `coverage_norms`: та принадлежит владельцу базы, и нужны были все недостающие поля разом (категория, даты действия, комментарий, автор), а главное — §9.2 требует ВЕРСИЙ, то есть нескольких строк на одну связку с разными периодами. Версия — это строка, а не атрибут строки, поэтому обычная боковая таблица «дополнительных полей» тут не годилась. Старая `coverage_norms` осталась пустой, вкладка «Нормативы» переведена на новый реестр. Единица хранения и расчёта — календарные ДНИ (§9), недели на экране из них выводятся. Уровней три: SKU, категория, «по умолчанию» для маркетплейса или пула; приоритет — SKU+рынок → SKU+пул → категория+рынок → категория+пул → по умолчанию+рынок → по умолчанию+пул, и он живёт ОДНОЙ функцией базы `coverage_norm_resolve()`, потому что его читают и загрузчик, и экран (второе написание разошлось бы молча). Статус §9.3 — функция `coverage_norm_status()`, границы включительно. Страна в реестре не хранится: и маркетплейс, и пул задают её однозначно.
- Статус относительно норматива считается ПО ТОМУ ЖЕ покрытию, что показано в строке, поэтому у двух оснований он разный: `norm_status` для темпа продаж, `plan_norm_status` для плана. Покрытие переводится в дни как «недели × 7» — точность статуса одна неделя, и меньше её не будет, пока проекция недельная; для порогов в 30–90 дней этого хватает. Пока реестр пуст, у всех строк `no_norm` — это состояние §9.3, а не сбой, и на «Остатках» оно подписано словом с числом строк. Значения нормативов заводит бизнес-аналитик (§9.2), поэтому ничего «по умолчанию» мы не выдумываем: пустой реестр честнее придуманных 30/60/90.
- Паспорт данных (`data_passport.py`, с 26.09.2026, пока Обзор и Автозаказ): у страницы объявлен список источников — таблица, колонка с датой СОДЕРЖИМОГО, что эта таблица кормит и какая джоба её обновляет. Из этого собираются три вещи: предупреждение наверху при устаревших данных, текст ⓘ у каждой цифры («данные по 25.09, обновляет Kabinet - Economics Loader») и блок «Откуда данные» внизу. Возраст считается по содержимому, а не по времени прогона джобы: пользователю важно, по какое число цифры. Пороги берутся из `data_freshness_rules` (там же, где их читает сторож) — в коде только дефолт на случай отсутствия правила, и в паспорте видно словом, откуда порог взялся. У источников, где тишина нормальна, проверка возраста выключена (`watch=False`): инциденты молчат, когда всё хорошо, а план месяца неделями не меняется по делу — иначе предупреждение висело бы там, где ничего не случилось. Один запрос на страницу (UNION ALL из MAX по каждому источнику плюс один по правилам), кеш 5 минут; отсутствующая таблица не роняет паспорт, а показывается строкой «нет данных»; любая ошибка чтения превращается в подпись «паспорт не прочитался» — цифры при этом остаются на экране.
- «nan» в пояснениях паспорта (пять строк на Обзоре, две на Автозаказе) — тот самый случай из раздела про `x or ""`: pandas отдаёт незаполненный `origin_note` как NaN, NaN в Python истинен, поэтому строка попадала в список пояснений и печаталась словом «nan». Приведение к тексту в паспорте теперь только через `util.as_text`.

- **Красная строка сверки ≠ ошибка: каждое расхождение раскладывается, и в сторож уходит только остаток** (с 03.10.2026). У строки `reconciliation_results` есть `explained`, `explanation` (словами) и `components` (слагаемые jsonb). Правила объяснения — только для ДОКАЗАННЫХ причин: (1) сдвиг по дням — за окно в допуске, за допуском отдельные дни; (2) порог значимости `recon_min_abs_eur` (20 €), только для денег, не для штук; (3) комиссия Amazon — ставка реферальной комиссии за штуку совпадает в пределах `recon_rate_tolerance_pct` (5 %): у Дарины модельная комиссия на все ЗАКАЗАННЫЕ штуки (`v_amazon_spiderweb_report`: `referal_fee + digital_fee + fba_fee`), у нас фактическая из `dnipro_m.kabinet.economics_fees` на отгруженные — отсюда −27…−42 % при ставке 9,91 против 9,70 € (ES); (4) комиссии ManoMano — без последних 8 дней сходятся (таблица недельная); (5) себестоимость — общие штуки сходятся, цена за единицу в пределах `recon_unit_cost_tolerance_pct` (6 %, дата себестоимости), штуки без нашей себестоимости называются числом. Блок «СВЕРКА» в `Kabinet - Watchdog` заводит `reconciliation` (`[RECON:источник/метрика/рынок]`, settlement — high, остальное — medium) только на `verdict = 'off' AND explained IS NOT TRUE`, по последнему расчёту не старше суток; закрывает сам, когда сошлось или объяснилось. Паспорт называет поимённо только необъяснённое. **Пробел наших данных — не объяснение**: заказы без цены в `orders_history` (FR, 2 заказа на 81 € 03.10) названы в тексте, но `explained = false` — сторож обязан о них сказать.
