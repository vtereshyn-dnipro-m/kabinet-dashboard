# kabinet-dashboard

Streamlit-дашборд поверх Databricks Lakebase (Postgres). Подключение — только через
`db/connection.py`, креды — только через `st.secrets`, никогда в коде.

## Как устроен этот файл (с 19.10.2026)

AGENTS.md — только правила работы и указатель. Подробности по областям (почему так, цифры сверок, история решений)
перенесены ДОСЛОВНО в `docs/` — файл правил разросся до 390 тыс. символов при лимите 150 тыс., и его хвост переставал
читаться. **Перед работой в области — прочитать её файл из указателя ниже.** Не нашёл в указателе — `grep -rn` по
`docs/`: раскладка фактов по темам сделана по ключевым словам, и факт мог лечь в соседний файл. Новое знание пишется в
файл своей области, а не сюда; сюда — только правило, которое касается любой работы.

## Автономия (предложение 19.10.2026; действует с мержа этого раздела владельцем)

Работа идёт циклами по `TASKS.md`. У каждой задачи там уровень — **сам**, **ждёт меня** или **никогда сам** — и
критерий готовности. Правило «Мерж — только по команде владельца, без исключений» ниже остаётся в силе для всего,
кроме уровня «сам»; уровень определяет не задача, а ИЗМЕНЕНИЕ: PR, который заходит хоть одним файлом выше уровня
«сам», становится «ждёт меня» целиком. Сомневаешься — уровень выше.

**Сам** — мержу без команды, если агент-проверяющий дал «ок» и обязательная проверка страниц зелёная; в сводке цикла
каждое такое слияние названо:
- `docs/` — только ДОБАВЛЕНИЕ строк (новый факт, новый файл области); изменение или удаление существующих строк
  `docs/` — «мержи»: там записаны решения владельца, и правка задним числом меняла бы их без него;
- `TASKS.md` — новые задачи, статусы, PR, заметки; уровень задачи агент может только поднять;
- комментарии в коде без изменения поведения;
- недостающие переводы в `i18n.py` (новый ключ или третий язык к существующему), если смысл фразы не меняется;
- проверочные скрипты в `scratchpad/`, которые только читают базу.
Без мержа и без команды (это не изменения): чтение данных и логов; пробы в `_probe` с `dry_run`/`probe=1` — у
отчётных загрузчиков только вне занятых слотов карты квоты `createReport`; открытие PR; прогоны проверок; запись
своей строки сводки в `kabinet_data.agent_cycle_reports` (`scratchpad/cycle_report.py` — единственный скрипт,
которому разрешена запись без команды).

**Только по «мержи #N»** (и выкладка — после мержа, как раньше):
- код страниц и модулей приложения, `requirements.txt`;
- ноутбуки `nb/`, патчи `nb/patches/`, настройки джоб `nb/jobs/` (расписание, триггеры, повторы, новые джобы);
- SQL: схема, данные, гранты, пороги в `reorder_params`, правила сторожа и свежести;
- правила в этом файле, изменение и удаление существующих строк в `docs/`, `docs/autonomy.md` целиком;
- `.claude/agents/` (проверяющий — им агент мог бы ослабить собственную проверку), `.claude/settings.json` и хуки;
- репозиторий Listing Suite.

**Никогда сам** — только владелец своими руками или с отдельного явного согласия названного человека:
- значения секретов: чтение, запись, перевыпуск (ключи кладёт владелец);
- режим входа `auth_enabled` и рубильник входа;
- удаление таблиц и данных (DROP, TRUNCATE, DELETE без условия), удаление чужих джоб и ноутбуков;
- код, настройки, расписание и таблицы владельца витрины — кроме перезапуска её Amazon-джоб самовосстановлением
  (разрешение 14.10.2026, `docs/power-bi.md`);
- действия, тратящие деньги или видимые снаружи: кнопки рекламы, отправка в Amazon из Listing Suite, сообщения людям
  (кроме бота владельцу), запросы отзывов покупателям;
- обход проверок разрешений, `--force` в `main`, мерж своего PR, где проверяющий дал замечания.

**Цикл.** 1) Прочитать `TASKS.md` и открытые PR. 2) Взять задачи по порядку; «ждёт меня» довести до PR и
остановиться. 3) Каждый PR — агент-проверяющий `.claude/agents/pr-reviewer.md` (отдельный агент, не автор):
вердикт «ок» / «замечания» комментарием в PR; замечания — исправить и проверить заново. 4) Смержить только уровень
«сам» с вердиктом «ок». 5) Обновить `TASKS.md` (статус, PR, что ждёт владельца). 6) Сводка в бот:
`scratchpad/cycle_report.py` кладёт её в `kabinet_data.agent_cycle_reports`, джоба `Kabinet - Agent Cycle Report`
отправляет — секрета бота агент не касается.
Не мержить и не выкладывать в окна, где идут цепочки: 09:30–11:30 (сборка витрины), 16:00–17:30 (вечерний Ledger).

## Ключевые правила одной строкой (подробности — в файле справа)

- Мерж — только по «мержи #N», кроме уровня «сам»; выкладка в Databricks — только после мержа; ноутбук из `nb/` после
  выкладки сверяется с репозиторием побайтно, основа патча — с живым ноутбуком.
- `auth_enabled = 0` открывает Кабинет всем без входа — только авария; вернуть 1 и сообщить владельцу (`docs/auth.md`).
- Ключи Amazon лежат в трёх местах; секрет не перезаписывать «на всякий случай» — сбросится счётчик срока
  (`docs/amazon-keys.md`).
- Джобы, ноутбуки и таблицы владельца витрины — только чтение (исключение — перезапуск самовосстановлением).
- Денежные цифры страниц = Power BI: страницы читают реплику, своей арифметики нет (`docs/power-bi.md`).
- Время Mirakl — часы Мадрида «как UTC»; длительности — только по `*_utc` (`docs/madrid-time.md`).
- Суммы GB/SE/PL — через вью `*_eur`; себестоимость уже в евро и не пересчитывается (`docs/currency.md`).
- Сегодняшний день — не день с данными; процент изменения — только между равными полными периодами
  (`docs/money-notes.md`).
- Перед PR со страницами — `scratchpad/smoke_full.py` на живой базе; AppTest не видит `st.data_editor`.
- Новая таблица — гранты обоим принципалам (приложение и джобы) в том же SQL.
- Значения из pandas — только `util.as_text`, `pd.isna`, `bool()`; не `or`, не `is`.
- У каждого типа тревоги — `inc.type.<код>` на трёх языках, иначе подпись по-русски или кодом.
- В справочниках — архив вместо удаления, удаление по одной записи через `confirm_delete()`
  (`docs/dictionaries-deletion.md`).

## Практики Databricks

### Каждая ячейка ноутбука самодостаточна

Ячейка заводит своё подключение и объявляет свои константы. Не полагаемся на то, что
выше по ноутбуку что-то уже выполнилось и оставило переменную в области видимости.

Причина в том, как ноутбуки реально исполняются: ячейку перезапускают в одиночку,
запускают с середины после падения, копируют в job — и любое состояние из соседних ячеек
в этот момент отсутствует или протухло. Ячейка, которая работает только при прогоне
сверху вниз, ломается ровно тогда, когда её отлаживают.

Дублирование подключений и констант здесь — не копипаста, а цена за то, что каждую
ячейку можно запустить в отрыве от остальных.

### `restartPython()` — один в ячейке, и ничего после него

`dbutils.library.restartPython()` перезапускает интерпретатор и обрывает
выполнение всего, что стоит после него в той же ячейке. «Run All» на этом
месте не падает, а молча останавливается: ни ошибки, ни красного — просто
остальной код не выполнился. Так ломались AMC Collect, FBA Ledger Detail
Loader и Stock Loader.

Поэтому установка пакетов — отдельная первая ячейка: `%pip install …` и
`restartPython()`, больше ничего. Весь код — со второй ячейки, и она
самодостаточна: после рестарта из первой не остаётся ни одной переменной.

Не полагаться на то, что `%pip` в новых рантаймах перезапускает Python сам:
где-то перезапускает, где-то нет, а ноутбук должен работать одинаково.

### Метка в `system_pulse` ставится в конце безусловно

Запись в `kabinet_data.system_pulse` — последняя операция ячейки, на верхнем уровне.
Не внутри `if всё_прошло:`, не внутри `try` рядом с полезной работой.

`system_pulse` — внешняя точка контроля: если умрут и сторож, и загрузчики, инциденты
никто не создаст, но метка перестанет обновляться, и это будет видно.

С 26.08.2026 в интерфейсе этого сигнала нет: плашку **состояния загрузчиков** с Обзора
убрали, клиенту живость джоб не показываем, и этот индикатор в дашборд не возвращаем.

С 26.09.2026 различие важно держать в голове: по решению владельца на страницах есть паспорт
данных — предупреждение наверху, когда **сами цифры** опираются на устаревшие данные, ⓘ у цифры
с источником и датой и блок «Откуда данные» внизу (`data_passport.py`). Это не плашка про
загрузчики: возраст считается по содержимому (последняя дата продаж, расчёта, снимка), про пульс
и джобы пользователю не говорится ничего. Пороги — из `data_freshness_rules`, те же, что у сторожа.

Единственный канал алертов по живости загрузчиков — Telegram. «Инциденты» сюда не
относятся: там данные о качестве самих данных, а это другой сигнал (см. абзац ниже).
Поэтому вопрос «почему цифры старые» с дашборда больше не отвечается — ответ в
Telegram и в `system_pulse` напрямую.

Метка, спрятанная в условную ветку, ломает этот контур в обе стороны: загрузчик отработал,
но по какой-то строгой проверке в ветку не зашёл — приходит алерт «загрузчик мёртв»,
хотя данные на месте. Ложные тревоги приучают не читать эти сообщения, и настоящий сбой
проходит незамеченным. Теперь, когда канал один и он в мессенджере, цена ложной
тревоги выше: на дашборде плашку можно было проигнорировать взглядом, а поток
неверных алертов в Telegram отключают целиком.

Из-за этого `last_success_at` по смыслу — «когда ячейка доработала до конца», а не
«когда всё внутри отработало без ошибок». За качество самих данных отвечают инциденты,
за живость загрузчика — пульс. Это разные сигналы, смешивать их в одном поле не надо.

### Проглоченная ошибка обязана дойти туда, где её прочтут

`try/except` вокруг проверки или отправки — нормально: одна упавшая проверка
не должна оставлять без присмотра остальные. Ненормально то, что делается в
`except`. `print("⚠️ …")` в лог джобы — это не логирование: лог никто не
открывает, джоба зелёная, пульс на месте. Именно так `Kabinet - Watchdog`
с 01.09 по 13.09.2026 на каждом прогоне печатал `Telegram error` и две
недели не отправил ни одного алерта, а `Suppressed Listings Checker` десять
дней падал на SSL-обрыве, и никто не заметил, потому что правила на него
не было.

Правило: ошибку, которую решили проглотить, кладём туда, где её увидят, —
в само сообщение Telegram отдельным блоком («⚙️ сбои проверок сторожа»),
в инцидент, в `_soft_errors`. А если проглатывать нельзя — как отправку
самого алерта — прогон должен упасть, но после записи пульса, чтобы падение
не превратилось в ложный «сторож мёртв». Молчание канала должно быть красным.

### Одно имя джоба в трёх местах

Имя джоба в Databricks, имя в метке `system_pulse` и `job_name` в правиле
`job_health_rules` — одна и та же строка, символ в символ. Расхождение не ломает
ничего явно, поэтому живёт месяцами и обнаруживается только сплошной сверкой.

Ломается это в обе стороны, и обе тихие.

Правило без метки: сторож ждёт имя, которое никто не пишет, и каждый день шлёт
«no success in N h» про живую джобу. Так было с `Kabinet - Review Requests
(Morning)` и `(ES Evening)` — два правила на два расписания, а ноутбук писал одну
метку `Kabinet - Review Requests`.

Метка без правила: джоба пишет пульс, но её никто не проверяет — умрёт молча.
Так остались без присмотра `Kabinet - MYI Report Collector`, `FBA Ledger Detail
Loader`, `Listing Cards Sync`, `CF Transactions Loader`, `MM Competitiveness Loader`.

Переименование даёт сразу обе поломки: старая метка застывает и выглядит мёртвой
джобой, новая пишется мимо правила. Именно так `Kabinet - AMC Collect` (метка от
31.08) породил ежедневный ложный алерт, пока живой `AMC Collect` писал рядом
каждые шесть часов.

Практическое следствие: переименовал джобу — правь метку в ноутбуке и `job_name`
в правиле тем же коммитом, а старую строку `system_pulse` удаляй. И не удаляй
метку только потому, что она просрочена: просроченная метка живой джобы — это
сигнал о поломке, а не мусор. Удалять можно лишь метку имени, которого в
Databricks больше нет.

Одна джоба — одна метка. Два пульса из одного ноутбука (`Kabinet - Economics
Loader` и `... (LM)`, записанные с разницей в три секунды) — это не два сигнала,
а один, размноженный: правило висит на одном имени, второе не проверяется никем.
Если у джобы есть режимы, которые надо различать (утро и вечер), то это разные
метки И разные правила, а не одна метка на оба.

### `_w` в ноутбуке — это WorkspaceClient, а не свободное имя

Во всех наших ноутбуках подключение к Lakebase собирает `pg()`, а имя пользователя и токен оно
берёт из модульного `_w = WorkspaceClient()`. Локальная переменная с тем же именем — например
`_w = _cur.fetchone()` — перекрывает клиент, и падает не та строка, где ошибка, а **каждое
следующее** обращение к базе: `AttributeError: 'tuple' object has no attribute 'current_user'`.

Так 26.09.2026 упал добор истории в `Kabinet - FBA Shipments Loader`: чтение настройки из
`reorder_params` положило кортеж в `_w`, и прогон умер на записи пульса, потратив впустую один
`createReport`. Ошибка выглядит как поломка SDK, а не как переименование переменной, поэтому
ищется дольше, чем стоит.

Правило: короткие имена `_w`, `_c`, `_cur` в этих ноутбуках уже заняты (клиент, соединение,
курсор) — своим переменным давать имена длиннее и по смыслу.

### Добор истории — кусками, и каждый шаг со своим соединением

Окно в полгода Amazon не собирает: прогон `Kabinet - FBA Shipments Loader` с окном 180 дней
26.09.2026 ждал отчёт 37 минут и не дождался, а следующая попытка 40 минут получала 429 на
`createReport` и упала с `[QUOTA_429]`. Историю добираем месячными кусками — `window_days` и
`window_end_days` в `reorder_params` задают начало и конец окна, по одному отчёту на кусок.

429 на `createReport` не долбим: квота общая на аккаунт продавца, и сорок попыток по минуте её не
освободят — кусок переносится на следующее тихое окно (по карте 01:00–02:30).

И отдельный урок того же вечера: **скрипт, который живёт часами, не должен держать одно соединение
с Lakebase.** Токен живёт около часа, и 80-минутное соединение умерло ровно на уборке в `finally` —
`setw(14, 0)` не выполнился, и в базе осталось окно «180–150 суток назад». Дневной прогон с ним
притащил бы кусок мая вместо свежих отгрузок. Каждый шаг долгого скрипта открывает своё соединение,
и уборка в `finally` — тоже своё.

### Квота `createReport` — общая на весь аккаунт

SP-API даёт на создание отчёта один запрос в минуту с запасом в пятнадцать, и
это лимит **аккаунта продавца**, не джобы. Его делят все загрузчики отчётов
разом: Returns, MYI, Suppressed Listings, Catalog Items, SQP Loader с его
очередью, FBA Charges. Когда двое сходятся во времени, второй получает 429 —
и не на секунды, а на десятки минут: backfill FBA Charges 13.09.2026 ждал
сорок минут подряд и упал.

Практическое следствие: новые загрузчики отчётов ставим на часы, когда
остальные молчат, — смотреть расписания через Jobs API, а не помнить. На
создании отчёта ждать терпеливо, минутами, и писать в базу по частям — чтобы
падение на седьмом отчёте не уносило шесть скачанных. Backfill на много
отчётов — только в тихое окно и с поднятым таймаутом джобы.

Data Kiosk и Finances API этой квоты не касаются — у них свои. Data Kiosk — 1 запрос и 1 скачивание документа в минуту
(запас 15) на аккаунт, и его занимают только наши джобы (сверка кода всех джоб 18.10.2026; джобы Дарины в него не
ходят): реплика Sales & Traffic (по записи ~10:30, запасной 11:00), Economics Loader (12:30–12:46), промо 08:50 и
ночной добор экономики 00:30–04:30. Новый загрузчик Data Kiosk ставить вне этих окон. Finances API (0,5 запроса в
секунду) вызывает только `Kabinet - Amazon Finances Loader` (08:40).

Карта createReport с 19.09.2026 вечера (Киев; в скобках обычная длительность), только джобы, которые
создают отчёты, — остальные квоту не трогают: 02:30 SQP (55 мин) · 03:30 ср Brand Analytics (9–20) · 04:00
Inventory Age (3) · 04:15 Account Health (5) · 04:30 SQP · 05:30 Suppressed Listings (9) · 06:00 Returns (6) ·
**06:15 Дарина FBA Fees + Listings (50)** · 07:15 MYI (1) · 07:30 FBA Charges (3) · **с 06.10.2026 07:00–~10:05 Дарина Sales & Traffic for Tableau (окно 10 дней × 10 рынков, отчёт в 1,5–2 мин — ниже скорости пополнения квоты)**; на неё накладываются MYI 07:15 и FBA Charges 07:30 (пн) — запаса квоты хватает, но если начнутся `[QUOTA_429]` по утрам, искать здесь · **10:20 Дарина Ledger Summary (1–8)** · 11:00 Ledger Detail + Listing

смотреть фактические длительности через `runs/list`, а не по памяти.

**Перед пробой или добором, которые создают отчёты, — живое расписание, а не эта карта** (правило с 16.10.2026).
Карта отстаёт: аналитик двигает свои джобы сам. Перед пачкой `createReport` смотреть в Jobs API расписания всех
джоб из карты, не ставить пачку ближе ~20 минут к чужому прогону, не больше 5–6 отчётов подряд и **на 429 не
повторять**. 16.10.2026 проба на 12 отчётов шла 16:06–16:33 и повторяла отказы каждые 65 с; Ledger Summary стоял уже
в 16:20, а не в 16:40, получил 429 трижды (плановый прогон и два перезапуска) и не записал ничего. Его ноутбук 429 не
показывает — прогон зелёный, поэтому проверять надо запись в таблицу (`DESCRIBE HISTORY`), а не статус прогона.
Отказы в тот день начались ещё в 15:30, до пробы: `Kabinet - FBA Shipments Loader` 87 минут стучался в Amazon по 40
попыток на автоповтор. Похоже, у отчётов FBA (отгрузки, утилизация, Ledger Summary) свой, более тесный лимит: отчёты по
купонам и возвратам в 16:08 создавались, пока отчёт отгрузок получал 429.

На 429 при createReport наши загрузчики ждут по минуте до 40 минут и падают с маркером `[QUOTA_429]`
в тексте ошибки (кроме `Kabinet - FBA Shipments Loader`: с 16.10.2026 он на 429 не ждёт и не повторяет — ни внутри
прогона, ни автоповтором джобы; отгрузки дочитывает следующий прогон, окно перечитывается целиком); сторож читает ошибку последнего прогона через `get_run_output` и заводит `report_quota`
(warning, дайджест в ClickUp) вместо `job_health` (critical) — квота и поломка кода различаются. До 19.09
Suppressed Listings на 429 печатал ERROR и молча пропускал рынок, Returns крутил рекурсию без предела.
Economics Loader (ячейка Sales & Traffic) до 19.09 на любой не-202 от createReport печатал `create failed` и
возвращал пустой список — рынок молча выпадал из `sales_traffic_daily`; теперь сбои рынков копятся, строки
остальных рынков и пульс пишутся, и ячейка падает после них (с `[QUOTA_429]`, если причина — квота).

### Квантификатор регулярки внутри f-строки — только в двойных скобках

SQL для Spark часто собирается f-строкой, и `'^[0-9]{6}'` внутри неё — это не
регулярка, а подстановка выражения `6`: шаблон молча превращается в `'^[0-9]6'`.
Ошибки нет, запрос выполняется, просто фильтр другой. Так `Kabinet - Stock
Loader` с 12.07 по 14.09.2026 брал из Odoo только SKU со второй цифрой 6 —
144 позиции на склад вместо ~3 000, и Мадрид в `warehouse_stock` показывал
133 штуки при 6 310 в источнике. Два месяца никто не заметил, потому что
строки были, просто мало.

Правило: в f-строке квантификаторы пишем `{{6}}`, `{{5,}}`; а лучше выносить
шаблон в переменную вне f-строки (как `NORM` там же рядом) и подставлять её.

## Связанные PR: ветку-основу удаляем последней

Когда второй PR основан на первом (`--base` — ветка первого, а не `main`), мерж первого
с удалением ветки **закрывает второй PR молча**: GitHub закрывает всё, что нацелено на
исчезнувшую базу. Переоткрыть нельзя — `reopen` отвечает «Could not open the pull request»,
смена базы у закрытого PR запрещена («Cannot change the base branch of a closed pull
request»), и восстановление ветки тем же коммитом не помогает. Остаётся перебазировать
ветку на `main` и выпустить новый номер: так #158 превратился в #159 (26.09.2026).

Ломается это тихо в том смысле, что мерж первого PR проходит успешно и ничего не сообщает
про второй — обнаруживается уже при попытке смержить его.

Практическое следствие: пока есть зависимый PR, первый мержим **без** `--delete-branch`,
затем переводим зависимый на `main` (`gh pr edit N --base main`) и перебазируем его ветку,
и только потом удаляем ветку-основу. Либо не связываем PR вовсе: второй сразу от `main`,
если правки не пересекаются по файлам.

## Слои данных

Три слоя, и у каждого свой хозяин по смыслу, а не по тому, кто первый успел.

| слой | где | что там |
|---|---|---|
| сырьё | `dnipro_m.raw_*` | ответ источника как есть: отчёт Amazon, выгрузка Mirakl, таблица Odoo. Одна таблица — один источник, без чистки и без бизнес-логики |
| расчёты | `kabinet_data` | то, что Кабинет считает поверх сырья: `economics_summary`, `coverage_summary`, справочники, инциденты, правила |
| витрины | вью поверх расчётов и сырья | что читают страницы и Tableau |

**Новый источник кладём в сырьё, не в свою базу.** Соблазн понятен: загрузчик
Кабинета, таблица в `kabinet_data`, всё под рукой. Но сырьё, спрятанное в слое
расчётов, для остальных не существует — Дарина не найдёт settlement-отчёты в
`kabinet_data`, заведёт свой загрузчик, и через месяц одни и те же отчёты Amazon
лежат в двух местах с разной глубиной и разными пропусками. Ровно так возникли
`raw_amazon_settlements_es` у неё и `raw_amazon_returns` у нас: обе про Amazon,
обе неполные, друг о друге не знают.

**Если источник уже собирается кем-то — не дублируем, а договариваемся о
переносе.** Прежде чем писать загрузчик, проверить `dnipro_m.raw_*` и спросить.
Нашёлся чужой, но неполный или заброшенный — расширяем его или забираем себе
целиком, с той же таблицей и теми же колонками, чтобы чужие вью не сломались.
Два загрузчика одного источника — это два хозяина строк, а к чему это приводит,
записано выше про LM в `economics_summary`.

Практическое следствие для Кабинета: `kabinet_data.raw_*` — это не сырьё, а
реплики и промежуточные выгрузки, которые Кабинету нужны локально в Lakebase.
Их первоисточник обязан лежать в `dnipro_m.raw_*`, и при расхождении прав тот,
что в `dnipro_m`.

## Пороги и правила живут в БД

Пороги свежести, здоровья загрузчиков и прочие правила лежат в `system_pulse`,
`data_freshness_rules`, `job_health_rules`. Код читает их оттуда и НЕ дублирует
константами.

Иначе правило меняют в базе, а поведение остаётся старым — и расхождение не видно
ниоткуда: в базе новое значение, на экране результат по старому, и оба выглядят
правдоподобно. Ищется это только чтением кода.

Три случая за два дня: фильтр маркетплейса, порог SQP, плашка свежести с зашитым
`hours_ago > 26`.

Практическое следствие: увидев в коде число, которое похоже на настройку — часы,
дни, доли, границы «нормально/плохо», — сначала проверь, нет ли для него строки в
БД. Если есть, читай оттуда. Если нет, но по смыслу должна быть, скажи об этом,
а не закрепляй константу.

## Метрики и фильтры качества

- Подстановки в переводы делаются через `t(key, a=..., b=...)`, а не `t(key).format(...)`. Обычный `.format()` на переводе бросает KeyError, когда набор плейсхолдеров в словаре и в коде разошёлся, — и это роняет страницу целиком вместо того, чтобы показать прочерк в одном месте. Расходятся они легко: фраза и код живут в разных файлах, а Streamlit Cloud после деплоя без полного перезапуска умеет держать старый модуль рядом с новым.
- `x or ""` для приведения к тексту не годится: NaN в Python истинен, поэтому выражение возвращает сам NaN и следующий `.lower()` падает; `pd.NA` бросает TypeError ещё на проверке истинности. Обёртка `str()` спасает от падения, но подставляет строку «nan», и та уезжает в таблицу как артикул. Единственная верная проверка — `pd.isna`, и живёт она в `util.as_text`.
- Фильтры качества данных не применяются к живому хвосту без явного индикатора отсева — три инцидента класса: обрыв графика отзывов, усыхание корзины тотала, молчаливый обрыв 16.08.
- Критерии аномалий строить на суточных скачках, не на размахе за окно.
