# TASKS — очередь работ Кабинета

Читается в начале каждого цикла и обновляется в конце (правила — AGENTS.md, раздел «Автономия»; схема —
`docs/autonomy.md`). Одна задача — одна запись. Уровень ставит владелец или агент при заведении; агент может только
ПОДНЯТЬ уровень (сам → ждёт меня → никогда сам), опустить — только владелец.

## Шаблон записи

```
### T-<номер>. <Коротко, что сделать>
- Уровень: сам | ждёт меня | никогда сам
- Критерий готовности: <проверяемый результат: что видно, какой цифрой, где; «PR открыт» — не критерий>
- Статус: в очереди | в работе | ждёт владельца: <чего именно> | готово DD.MM
- PR: #N (вердикт проверяющего: ок / замечания)
- Заметки: <решения, ссылки на docs/, что выяснилось>
```

Уровни (подробно — AGENTS.md):
- **сам** — агент доводит до конца, включая мерж (только `docs/`, `TASKS.md`, переводы, проверочные скрипты);
- **ждёт меня** — агент доводит до PR, проверки и описания; мерж и выкладка — по «мержи #N»;
- **никогда сам** — агент готовит план или черновик, делает владелец (секреты, вход, чужие джобы, деньги, удаление).

  ровно ожидаемые («Проверка после» в заметках). `smoke_ls_auth.py` и `smoke_full.py` — 0 провалов. Вход в Кабинет и
  Listing Suite работает, рубильник отвечает: проверка только чтением, `get_auth_mode()`.
- Статус: ждёт владельца — решение, кому владеть, и окно для смены
- PR: —
- Заметки (выяснено чтением 22.10.2026; предложение, кода нет; поправлено по проверке PR #367):
  - **Почему это важно.** `claude_code_ro` — подключение агентов (MCP, проверки), и вопреки имени оно не «только
    чтение». В `kabinet_data` ему принадлежат 118 таблиц, 25 вью, 33 последовательности и 18 функций. Среди них все
    таблицы входа: `app_users`, `app_permissions`, `app_user_countries`, `app_login_log`, `app_action_log`,
    `app_deploy_log`, `qa_tokens`, `reorder_params` (там и рубильники `auth_enabled` / `ls_auth_enabled`), функция
    триггера `app_permissions_keep_admin` и три функции, которые выполняются с его правами (SECURITY DEFINER):
    `app_user_bind_sub(text, text)` — привязка входа через Google (`auth.py`), `get_auth_mode()` и
    `set_auth_mode(integer)` — рубильник (`nb/auth_switch.py`). Владелец таблицы может всё без грантов: менять CHECK,
    выключить триггер защиты администратора, удалить таблицу. Защита от самоблокировки и правило «вход — никогда сам»
    держатся на дисциплине агента, а не на правах. 22.10.2026 это и понадобилось: SQL роли пилота меняет CHECK, а это
    может только владелец таблицы — пришлось давать агенту разовое исключение.
  - **Кому владеть.** Не человеку напрямую: человек уходит, а роль остаётся. Не `claude_code_rw`: в нём `claude_code_ro`
    состоит с INHERIT и SET, и ничего бы не изменилось. Предложение — новая групповая роль без входа (например,
    `kabinet_owner`), в ней — владелец Кабинета; агентские подключения в неё не входят.
  - **Что передать одним заходом** — иначе сломается вход:
    - восемь таблиц;
    - их последовательности: `app_login_log_id_seq`, `app_action_log_id_seq`, `app_deploy_log_id_seq`,
      `qa_tokens_id_seq` (принадлежат таблицам и уходят вместе с ними — проверить);
    - функцию триггера и три SECURITY DEFINER-функции. Если их не передать, `app_user_bind_sub` после смены выполнится
      с правами `claude_code_ro`, а у него уже не будет записи в `app_users` — вход через Google упадёт.
  - **Как сменить, по порядку (одна транзакция).** В PG 17 `ALTER … OWNER TO` требует трёх вещей сразу: быть
    владельцем объекта (или наследовать его права), уметь `SET ROLE` в новую роль и чтобы у новой роли было CREATE на
    схему.
    1. Создать групповую роль. Явно вступить в неё с INHERIT и SET: на базе пустой `createrole_self_grant`, и создатель
       получает только ADMIN.
    2. Дать новой роли USAGE и CREATE на схему `kabinet_data` (схема принадлежит владельцу Кабинета, он выдаст сам).
    3. Дать себе на время INHERIT на `claude_code_ro` — явно `WITH INHERIT TRUE, SET FALSE`: в PG 16+ у нового гранта
       роли SET по умолчанию включён. Сейчас у владельца там только ADMIN.
    4. Передать новой роли всё из списка выше.
    5. В той же транзакции выдать `claude_code_ro` SELECT на восемь таблиц. Это не только для проверок: три вью
       `claude_code_ro` читают `reorder_params` с правами владельца — `v_sku_abc` (страница «Остатки»),
       `v_marketplace_data_status` («Справочники» и сторож), `v_load_day_completeness`. Без SELECT они отдадут
       `permission denied` всем, включая приложение.
    6. Снять с себя INHERIT на `claude_code_ro` — ту строку гранта, которую выдал себе сам, а не строку от `cloud_admin`
       (`REVOKE … GRANTED BY`).
    - Гранты, которые выдал старый владелец, Postgres переносит на нового. Права приложения (`583bf6d1-…`), джоб
      (`b1698364-…`) и Listing Suite останутся.
  - **Проверка после.** Сравнить `aclexplode` до и после по восьми таблицам, четырём последовательностям и четырём
    функциям. Ожидается: строки приложения, джоб и Listing Suite прежние, грантор — новая роль; строка прав самого
    `claude_code_ro` стала строкой новой роли; у `claude_code_ro` новая строка SELECT. Затем `smoke_ls_auth.py`,
    `smoke_full.py`, вход в Кабинет и Listing Suite, проба рубильника `nb/auth_switch.py` только чтением
    (`get_auth_mode`).
  - **Решение владельца — `reorder_params`.** Там не только рубильники входа, но и пороги: её упоминают 62 файла в `sql/`.
    После смены владельца каждая выкладка SQL по «мержи», которая меняет `reorder_params`, идёт через `SET ROLE` в новую
    роль, а не под `claude_code_ro`. Варианты: передать таблицу целиком (пороги тоже меняет только владелец) или
    вынести рубильники в отдельную таблицу новой роли, а `reorder_params` оставить как есть.
  - **Где ещё поправить.** В шапках SQL `migrations/kabinet/` (Listing Suite) и `sql/` (Кабинет) указано «от роли
    Кабинета (она владеет app_users и app_permissions)». После смены владельца эти файлы выполняются под новой ролью
    через `SET ROLE`.
  - **Когда.** Смена владельца коротко берёт исключительную блокировку таблицы: вход на секунды встанет в очередь.
